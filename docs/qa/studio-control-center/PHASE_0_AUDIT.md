## 1. КРАТКОЕ ОПИСАНИЕ СУЩЕСТВУЮЩЕЙ АРХИТЕКТУРЫ

Critical Save Studio представляет собой **монолитное серверное веб-приложение на Python (Flask 3.1 + SQLAlchemy 2.0)** с динамическим SSR (Server-Side Rendering) на Jinja2, локальным хранилищем SQLite и кастомной дизайн-системой **Critical Noir**:

1. **Серверная часть:**
   - Монолит Flask со структурой Application Factory (`app/__init__.py`).
   - Маршрутизация разделена на два Blueprint:
     - `public_bp` (`app/routes/public.py`): публичные страницы каталога, игр, программного обеспечения (Financial War Room), статей, вакансий и обработки форм.
     - `admin_bp` (`app/routes/admin.py`): базовая административная панель с URL-префиксом `/admin`.
   - Поддерживает сессии на базе зашифрованных cookie (`SESSION_COOKIE_HTTPONLY = True`, `SESSION_COOKIE_SAMESITE = 'Lax'`).
   - Защита от CSRF реализована в `app/services/csrf.py` с проверкой токена в `admin_bp.before_request`.
2. **База данных и данные:**
   - Локальная база данных SQLite: `data/critical_save.db` (инициализируется и наполняется через `seed_db.py`).
   - Модели данных (`app/models/__init__.py`):
     - `User`: учётные записи администраторов с хэшированием паролей bcrypt (`id`, `username`, `password_hash`, `role`, `is_active`, `last_login`).
     - `Game`: проекты студии с двуязычными полями (`title_en`/`title_ru`, `tagline_*`, `short_description_*`, `full_description_*`, `genre_*`, `status_*`, `platforms`, `release_date_info`, JSON-массивами изображений галереи и фичей).
     - `Article`: публикации студийного журнала (`slug`, `title_*`, `content_*`, `excerpt_*`, `category_*`, `cover_image`, `reading_time_minutes`, `is_published`).
     - `Career`: открытые вакансии студии с двуязычными описаниями и требованиями.
     - `ContactInquiry`: очередь входящих сообщений (`name`, `email`, `subject`, `message`, `status`, `ip_address`).
     - `StudioSetting`: key-value хранилище для глобальных настроек (хранит JSON).
3. **Локализация:**
   - Строки интерфейса и системные метки хранятся в кодовом словаре Python: `app/services/i18n.py` (`TRANSLATIONS["en"]` и `TRANSLATIONS["ru"]`).
   - Контент сущностей (игры, статьи, вакансии) локализован на уровне базы данных (`_en` и `_ru` колонки).
   - Префиксная маршрутизация URL: `/<lang>/...` (`en` по умолчанию, `ru`).
4. **Статические ресурсы и дизайн-система:**
   - `app/static/css/main.css`: монолитный файл стилей (более 5400 строк), содержащий токены Critical Noir (`--color-noir-void: #0B0B12`, `--color-noir-obsidian: #12121C`, `--color-noir-violet: #8B78E6`), сетки и медиа-запросы адаптивности от 320px до 1440px+.
   - `app/static/js/main.js`: клиенсткая логика переключения темы (Dark/Light/System), мобильного меню, копирования SHA-256 и карусели Hero-карточки.
   - `app/static/images/artwork/`: оригинальные графические арты высокого разрешения (`.jpg`) и векторный логотип (`logo.svg`).
   - `app/static/uploads/`: локальная папка загрузки медиафайлов.
5. **Git и CI/CD статус:**
   - Каталог `C:\Users\PLATINUM\.gemini\antigravity\scratch\critical_save_studio` в настоящее время **НЕ является инициализированным Git-репозиторием** (каталог `.git` отсутствует, `git status` возвращает `fatal: not a git repository`).
   - Папка `.github/` и конфигурации GitHub Actions / GitHub Pages на текущий момент отсутствуют.
   - Сайт в текущем виде подготовлен к запуску через WSGI/ASGI сервер (`python run.py`, порт 5000), а не как статически экспортированный сайт.

## 3. РЕАЛЬНЫЕ ВОЗМОЖНОСТИ И ОГРАНИЧЕНИЯ СУЩЕСТВУЮЩЕЙ АДМИНКИ

Текущая панель `/admin/` **не является полноценной CMS**, а представляет собой базовый CRUD-интерфейс для разработчика:

### Что есть сейчас:
1. **Аутентификация:** Форма входа `/admin/login`, валидация логина и bcrypt-хэша пароля, сессионный cookie, выход `/admin/logout`.
2. **Управление играми (`/admin/games`):** Создание, редактирование и удаление записей в таблице `games`. Загрузка обложки (`cover_file`) и фонового арта (`hero_file`) через `save_media_file`.
3. **Управление статьями журнала (`/admin/articles`):** Создание, редактирование, удаление, статус публикации (`is_published`), выбор категории.
4. **Управление вакансиями (`/admin/careers`):** Создание, редактирование требований, локация, статус публикации.
5. **Просмотр сообщений обратной связи (`/admin/inquiries`):** Список заявок, смена статуса (`new`, `processed`, `archived`).
6. **Защита CSRF:** Проверка токенов на POST/PUT/DELETE.

### Критические ограничения существующей панели:
1. **Отсутствие управления Financial War Room и софтом:**
   - Страница `/ru/products/financial-war-room` и `/en/products/financial-war-room` захардкожена в шаблоне `product_fwr.html`.
   - Релизные метаданные (версия `4.1.0`, даты, размеры файлов, контрольные суммы SHA-256, пути к файлам на диске `dist-release`) захардкожены в словаре `fwr_metadata` в коде `app/routes/public.py` (строки 47–73) и в эндпоинте `download_fwr` (строки 80–89).
   - В админке **нет раздела Releases, нет модели Software / Products**, и администратор не может обновить версию ПО или SHA-256 без редактирования кода Python.
2. **Отсутствие управления текстовыми страницами и блоками (Pages):**
   - Главная страница (`index.html`), раздел "О студии" (`about.html`), страница контактов и тексты манифестов не имеют интерфейса редактирования.
   - Изменение формулировок, слоганов, преамбул разделов требует прямого изменения Python-файла `app/services/i18n.py` или шаблонов Jinja.
3. **Отсутствие медиабиблиотеки (Media Library):**
   - Нет каталога загруженных файлов, предпросмотра, поиска, оптимизации и безопасного удаления неиспользуемых ассетов.
4. **Однопользовательская / плоская ролевая модель:**
   - Модель `User` содержит поле `role`, но в коде маршрутов нет дифференциации прав (`Owner` vs `Editor`). Любой аутентифицированный пользователь имеет полные права на удаление любых объектов. Нет механизма приглашения второго пользователя, сброса пароля или аудита авторства изменений.
5. **Отсутствие версионирования, черновиков страниц и безопасной публикации:**
   - Все изменения в админке пишутся напрямую в рабочую базу данных SQLite (`db.session.commit()`).
   - Нет понятия «Черновик страницы» (Draft) vs «Опубликованная версия» (Published) для страниц сайта.
   - Нет предварительного просмотра (Staging / Live Preview), нет журнала ревизий и нет кнопки отката (Rollback).
6. **Невозможность удалённой совместной работы без деплоя:**
   - Сервер привязан к локальному `127.0.0.1:5000` и локальным абсолютным путям к файлам на диске `C:\Users\PLATINUM\...`. Без безопасного серверного развёртывания второй пользователь не имеет доступа к панели.

## 5. РЕКОМЕНДОВАННАЯ АРХИТЕКТУРА И ЕЁ ОБОСНОВАНИЕ

### Рекомендация: Вариант C (Эволюционное развитие существующего Flask Control Center с двухконтурной моделью публикации «Draft / Published»)

#### Обоснование выбора:
1. **Сохранение инвестиций в качество:** В рамках итераций 1–3.1 была выстроена и выверена безупречная дизайн-система Critical Noir (типографика Cinzel, сетки 320–1440px, интерактивные фильтры каталога, карточки FWR, тёмная и светлая темы, 15 автоматических тестов). Ломать этот фундамент ради чужой SaaS-платформы нерационально и несёт высокие риски регрессий.
2. **Нулевая зависимость от сторонних платных CMS:** Панель полностью принадлежит студии. Нет риска закрытия бесплатного тарифа внешней платформы, навязанных баннеров или блокировки аккаунтов.
3. **Безопасное управление релизами Financial War Room:** Только в серверной модели можно реализовать строгий шлюз проверки установщиков (хеширование файла, сверка байтов, валидация версий) перед выставлением ссылки на скачивание.

#### Концепция двухконтурной публикации (Publishing Pipeline):
- В базе данных каждая сущность (`Game`, `Article`, `PageContent`, `SoftwareRelease`) получает версионирование:
  - `draft_data_json`: текущее рабочее состояние, которое редактируют Owner и Editor.
  - `published_data_json`: зафиксированное утверждённое состояние, которое отдаётся посетителям сайта.
- **Preview-режим:** Кнопка «Предпросмотр» в Control Center открывает сайт со специальным временным безопасным токеном сессии, рендеря черновики без их публичного раскрытия.
- **Staging / Publication Gate:** Кнопка «Опубликовать изменения» доступна только роли **Owner**. Перед публикацией система автоматически прогоняет валидатор (наличие переводов RU/EN, корректность URL, существование ассетов, целостность SHA-256).
- **Экспорт / Синхронизация:** При необходимости размещения на GitHub Pages система может автоматически запускать скрипт заморозки (Static Freeze) и пушить готовый артефакт в ветку `gh-pages` через GitHub API с токеном репозитория.

## 6. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ К БУДУЩЕЙ CMS

### 6.1. Минимальная структура разделов Studio Control Center

```

├── [2] Pages & Sections   # Управление текстами и блоками (Home, About, Contact, Manifesto)

├── [4] Software & Tools   # Программные продукты, ключевые фичи, технические требования

```

### 6.2. Механизм структурированных контент-блоков (Block Engine)
Чтобы исключить случайное разрушение верстки Critical Noir неквалифицированным редактированием сырого HTML/CSS, все страницы собираются из **строго типизированных блоков**:
- `HeroBlock`: слоган 1, слоган 2, акцентный текст, фоновый арт, ссылки кнопок.
- `DivisionSplitBlock`: карточка направления (Games / Software), описание, метка, иконка.
- `ShowcaseGridBlock`: выбор отображаемых проектов из базы, лейбл секции.
- `ManifestoPillarBlock`: аксиома (номер, название, описание, статус).
- `EditorialTextBlock`: форматированный текст с поддержкой безопасного подмножества Markdown (жирный, курсив, списки, ссылки).

Администратор заполняет только текстовые поля и выбирает изображения из Медиабиблиотеки. Шаблоны Jinja2 гарантируют сохранение сетки, отступов и цветов Critical Noir.

### 6.3. Ролевая модель доступа (RBAC)

1. **Owner (Владелец студии):**
   - Полный доступ ко всем разделам.
   - Управление командой (создание, деактивация аккаунтов Editor, сброс паролей).

## 7. БЕЗОПАСНОСТЬ И ШЛЮЗ ПУБЛИКАЦИИ РЕЛИЗОВ

### 7.1. Требования к безопасности панели
- **Изоляция административных маршрутов:** панель администрирования закрыта строгой сессионной аутентификацией. Никакие эндпоинты `/admin/api/*` не должны быть доступны без действующей сессии.
- **Отсутствие клиентских секретов:** Токены GitHub API, пароли к БД, секретный ключ Flask (`SECRET_KEY`) хранятся исключительно в серверных переменных окружения. В публичном JavaScript админки передаются только одноразовые CSRF-токены.
- **Защита загрузки файлов (Media Guard):**
  - Валидация расширения (`.jpg`, `.jpeg`, `.png`, `.webp`, `.svg`).
  - Проверка MIME-типа и реальных байтов заголовка (magic bytes).
  - Санитизация имени файла (исключение directory traversal `../../`).
  - Лимит размера файла (16 МБ).
  - Запрет на исполнение скриптов в папке загрузок (`Content-Disposition`, правильные заголовки `Content-Type`).
- **Журнал аудита (`audit_logs`):** фиксация каждого действия: `timestamp`, `user_id`, `action` (`create_game`, `edit_release`, `publish_site`, `rollback`), `target_id`, `ip_address`.

### 7.2. Release Verification Gate для Financial War Room (Исключение публикации непроверенных установщиков)
*Контекст:* В ходе предыдущих итераций был выявлен критический блокер: сборка v4.2.0 содержала некорректный бэкенд, и публикация на сайт была заблокирована в пользу проверенной версии v4.1.0.

Чтобы навсегда исключить человеческий фактор и случайную публикацию поврежденного установщика, в CMS внедряется **4-ступенчатый шлюз релизов**:
1. **Физическая проверка файла:** При указании пути к инсталлятору система проверяет его фактическое наличие и доступность на чтение.
2. **Автоматический расчёт хэша на сервере:** Администратор не вводит SHA-256 вручную из буфера обмена. CMS самостоятельно вычисляет SHA-256 по телу файла и сверяет его с предоставляемым билд-манифестом.
3. **Флаг верификации бэкенда (`backend_verified = True`):**
   - Наличие правильного размера и хэша инсталлятора **не является** достаточным условием для публикации.
   - Установщик обязан иметь статус `Backend Architecture Verified: PASSED` (подтверждение того, что упакованный исполняемый файл был запущен в тестовой песочнице и успешно отвечает на внутренние запросы).
4. **Owner-Only Confirmation:** Только Owner может перевести статус релиза в `LIVE_PRODUCTION`.

## 8. АНАЛИЗ ВАРИАНТОВ БЕСПЛАТНОГО / БЮДЖЕТНОГО РАЗМЕЩЕНИЯ

Проведён анализ официальных лимитов и тарифов актуальных платформ (по состоянию на 2026 г.):

### Комбинация 1: GitHub Pages (Публичный фронтенд) + GitHub Actions (CI/CD) + Серверная панель управления
- **GitHub Pages:**
  - *Бесплатный тариф:* Полностью бесплатно для публичных репозиториев (и приватных на GitHub Free с ограничениями).
  - *Лимиты:* Размер репозитория рекомендован до 1 ГБ (жесткий 5 ГБ); лимит сборки сайта 1 ГБ; лимит трафика 100 ГБ в месяц; лимит сборок 10 сборок в час.
  - *Дистрибутивы ПО:* Инсталляторы FWR (155 МБ и 610 МБ) **нельзя** хранить в Git-репозитории (лимит файла 100 МБ). Их необходимо размещать в GitHub Releases (лимит файла до 2 ГБ бесплатно) или внешнем S3/R2.
- **GitHub Actions:**
  - *Бесплатный тариф:* 2000 минут выполнения в месяц для приватных репозиториев, неограниченно для публичных. Этого более чем достаточно для компиляции и деплоя сайта (сборка занимает ~30 секунд).

### Комбинация 2: Cloudflare Pages + Cloudflare Workers / D1 + Cloudflare R2
- **Cloudflare Pages:**
  - *Бесплатный тариф:* Неограниченная пропускная способность, неограниченное количество запросов. 500 сборок в месяц на бесплатном плане. Лимит размера отдельного статического файла — 25 МБ.
- **Cloudflare D1 (Serverless SQL Database):**
  - *Бесплатный тариф:* Хранилище 5 ГБ. Лимит чтения: 5 миллионов строк в день. Лимит записи: 100,000 строк в день. (Для студийного сайта трафик редактирования в 100 раз ниже лимитов).
- **Cloudflare R2 (Хранение ассетов и инсталляторов):**
  - *Бесплатный тариф:* 10 ГБ хранения в месяц бесплатно. Нулевая стоимость исходящего трафика (Zero egress fees). Запись: 1 миллион операций Class A в месяц. Чтение: 10 миллионов операций Class B.
  - *Идеально подходит* для раздачи инсталляторов Financial War Room (155 МБ и 610 МБ) без превышения лимитов.

### Комбинация 3: Standalone Flask на облачной платформе (Render / Fly.io / Селф-хостинг на VPS)
- **Render / Fly.io Free:**
  - *Особенности бесплатных планов:* Бесплатные инстансы (Web Services) засыпают после 15 минут неактивности (холодный старт 30–50 секунд). Для публичного портфолио задержка первого открытия неприемлема.
- **Рекомендация для продакшна:**
  - Использовать **Cloudflare Pages / GitHub Pages для публичного сайта** (100% аптайм, моментальная загрузка по всему миру через CDN, нулевая стоимость).
  - Панель **Studio Control Center** развернуть на выделенном защищённом поддомене (`control.criticalsavestudio.com`) либо локально/на микро-VPS ($4–5/мес), где холодный старт не мешает посетителям студии.

## 9. ПЛАН ПОЭТАПНОЙ РАЗРАБОТКИ STUDIO CONTROL CENTER

Все этапы спроектированы по принципу минимального воздействия на существующий продакшн с обязательной верификацией:

```
[Phase 1] Архитектура БД и модели ──> [Phase 2] Аутентификация и RBAC ──> [Phase 3] Управление контентом
                                                                                     │
[Phase 6] Бэкапы и финал ─────────── [Phase 5] Шлюз публикаций и QA ──── [Phase 4] Релизы и медиа
```

### Phase 1: Минимальная архитектура и модель контента
- **Задачи:**
  - Инициализация Git-репозитория проекта с чистым `.gitignore` (исключение файлов SQLite и секретов).
  - Расширение моделей данных: добавление таблиц `SoftwareProduct`, `SoftwareRelease`, `PageContent`, `AuditLog`.
  - Добавление полей версионирования (`draft_json`, `published_json`).
- **Критерии приёмки:** Миграция выполняется без потери существующих данных; unit-тесты моделей проходят успешно.

### Phase 2: Авторизация и управление доступом (Team & Access)
- **Задачи:**
  - Реализация ролевой модели `Owner` и `Editor`.
  - Защита сессий: привязка к User-Agent/IP, таймаут неактивности, ограничение попыток входа (Rate Limiting).
  - Интерфейс управления пользователями для Owner: создание учётки для друга, сброс паролей.
- **Критерии приёмки:** Editor не имеет доступа к критическим настройкам; попытки подбора пароля блокируются; сессии изолированы.

### Phase 3: Редактирование страниц, игр и программ (Content Engine)
- **Задачи:**
  - Создание интерфейса блочного редактирования страниц (Главная, О студии, Манифест).
  - Вынос словаря локализации интерфейса (`app/services/i18n.py`) в базу данных с возможностью правки в UI.
  - Полнофункциональный редактор игр и вакансий с синхронной валидацией RU и EN полей.
- **Критерии приёмки:** Правка любого текста в админке меняет предпросмотр без искажения стилей Critical Noir.

### Phase 4: Медиабиблиотека, локализации и релизы FWR
- **Задачи:**
  - Раздел Media Library: предпросмотр, тегирование, автоматическая генерация WebP и thumbnail.
  - Раздел Releases & Downloads: автоматический расчет SHA-256 и размера файла при указании установщика.
  - Внедрение проверки `backend_verified` перед активацией релиза.
- **Критерии приёмки:** Невозможно сохранить релиз с несовпадающим SHA-256 или ненайденным файлом; медиафайлы корректно отдаются.

### Phase 5: Предпросмотр, валидация и шлюз публикации (Publishing Engine)
- **Задачи:**
  - Механизм Preview: просмотр сайта с черновиками до публикации.
  - Кнопка «Опубликовать изменения» (только для Owner) с предварительным чек-листом валидации.
  - Пайплайн экспорта/сборки статических страниц и выгрузки на хостинг.
- **Критерии приёмки:** Черновики не видны анонимным пользователям; публикация атомарна; при ошибке сборки боевой сайт не ломается.

### Phase 6: Резервное копирование, откат и итоговый аудит
- **Задачи:**
  - Автоматическое создание снимка БД и контента перед каждой публикацией.
  - Механизм отката на 1 клик (Rollback to previous release).
  - Полный регрессионный тест всех разрешений (1440, 768, 390, 320px) и страниц.
- **Критерии приёмки:** Откат восстанавливает предыдущее состояние сайта менее чем за 1 минуту; все 15 тестов зеленые.

## 10. НЕИЗВЕСТНЫЕ ВОПРОСЫ И РИСКИ

1. **Отсутствие Git-репозитория в рабочей папке:**
   - *Факт:* Папка `C:\Users\PLATINUM\.gemini\antigravity\scratch\critical_save_studio` не инициализирована как git-репозиторий.
   - *Риск:* До инициализации Git и привязки к удалённому GitHub-репозиторию невозможно настроить GitHub Actions и GitHub Pages.
   - *Решение:* На фазе 1 выполнить контролируемую инициализацию `git init` с корректным `.gitignore`.
2. **Размещение тяжелых бинарных установщиков (155 МБ и 610 МБ):**
   - *Факт:* Файлы установщиков превышают лимит стандартных репозиториев GitHub (100 МБ).
   - *Решение:* Дистрибутивы FWR должны отдаваться через GitHub Releases, Cloudflare R2 или выделенный storage-сервер, а на сайте размещаться подписанные CDN-ссылки.
3. **Хранение секретов при совместной работе:**
   - *Риск:* Случайная утечка паролей или `SECRET_KEY` при передаче доступа второму пользователю.
   - *Решение:* Использование индивидуальных аккаунтов, отсутствие секретов в репозитории, файл `.env` остаётся строго на сервере.
